# “共享仓库”v0.1.1 运行时修复设计

## 背景

《鼠托邦》v1.0.0600 能通过 BepInEx 5.4.23.5 发现并加载“共享仓库”v0.1.0，六组 Harmony 补丁也能成功安装，但运行时协调器没有完成初始化。当前实现仅由 `Plugin.Update()` 调用会话轮询；实际运行日志在游戏完成读档后没有出现初始化成功或失败记录，导致所有受 `RuntimeReady` 保护的功能被跳过。

本次修复只保证 Mod 功能正常，不修复、推测或去重旧存档中已经存在的材料数量。旧存档当前序列化了多少材料，初始化时就按现有规则合并多少材料。

## 目标与范围

发布 v0.1.1，保持原有功能范围：

- 仅处理仓库 `BuildingName.Storage / 100` 和迷你仓库 `BuildingName.MiniStorage / 181`。
- 不处理电力仓库 `BuildingName.ElecStorage / 360`。
- 目标仓库共享同一个 `List_TileObj`。
- 目标仓库的材料种类容量为正无穷，界面显示“当前种类数/∞”。
- 新建仓库自动接入，拆除非最后一座仓库时不丢失或复制材料。
- 保存、资源统计、建造判断和账本统计只计算共享库存一次。
- 不添加配置开关、快捷键或旧存档修复工具。

## 方案比较

### 方案 A：由 `TileMgr.Update` Harmony 补丁驱动（采用）

在游戏自身必定执行的 `TileMgr.Update` 后置补丁中调用插件的会话轮询。每帧只做常量级守卫检查；达到轮询间隔后才读取管理器并尝试初始化。这样继续沿用现有协调器和异常回滚机制，同时避开未执行的 `Plugin.Update()` 生命周期入口。

优点是目标方法稳定、补丁系统已被日志证明可用，并且能自然覆盖读档、新游戏和切换会话。缺点是存在每帧一次方法调用，但守卫成本很低。

### 方案 B：补丁地图载入协程的完成状态

直接补丁 `TileMgr.MakeMapC` 的编译器生成状态机，在 `m_GameLoading` 变为 `false` 时初始化。触发时机精确，但强依赖编译器生成类型和 IL 状态，小版本更新后更容易失效，测试和诊断也更困难。

### 方案 C：场景事件加延迟协程

监听 Unity 场景切换，并在进入游戏场景后启动等待协程。实现直观，但仍依赖插件对象自身的 Unity 消息与协程生命周期，和本次故障属于同一风险类别，因此不采用。

## 结构设计

### 插件入口

`Plugin.Awake()` 继续负责创建协调器、安装 Harmony 补丁和记录加载日志。删除 `Plugin.Update()`，避免保留两个可能竞争的轮询入口。

将原有私有会话轮询整理为可由补丁调用的内部方法。该方法必须：

1. 在 Harmony 安装失败时立即返回。
2. 使用 `Time.unscaledTime` 保留 0.5 秒轮询间隔。
3. 读取当前 `GameMgr.Instance._BuildingMgr` 与 `_TileMgr`。
4. 离开游戏或管理器不存在时重置上一会话。
5. 管理器实例变化时重置并开始新会话。
6. `m_GameLoading` 为 `true` 时不修改库存。
7. 载入完成且本会话尚未初始化时调用协调器。
8. 初始化异常时回滚、记录一次明确错误，并允许下一轮重试。

### Harmony 生命周期驱动

新增针对 `TileMgr.Update` 的后置补丁。补丁只调用插件的安全轮询入口，不直接读取或修改仓库列表。若补丁入口本身发生异常，使用现有日志通道记录，不把异常传播到游戏循环。

这种分工保证 Harmony 层只负责接入，库存合并和会话状态仍由 `Plugin` 与 `StorageInventoryCoordinator` 管理。

### 库存与容量

`StorageInventoryCoordinator` 的合并规则保持不变：

- 按仓库 `m_ID` 升序选择主仓库。
- 按 `TileType` 合并材料项。
- 原样保留各库存中的全部 `List_Reservation` 条目。
- 所有目标仓库最终引用同一个共享列表。
- 对仓库和迷你仓库应用正无穷材料种类容量。

本次不识别历史重复库存，不根据相似度、预留编号或旧存档编号删除材料。

### 新建、拆除、统计与保存

已有 Harmony 接口继续使用，但只有在运行时协调器就绪后操作共享库存：

- `Building_Storage.BuildingSet` 后置补丁接入新仓库。
- `Building_Storage.BuildingDemolition(bool)` 在拆除前安全分离，最后一座使用原版行为。
- `PlayDataMgr.Save` 以及库存统计入口使用可嵌套、异常安全的单仓视图。
- `BI_StorageUI.InfoUpdate` 将目标仓库容量显示为“当前材料种类数/∞”。

## 错误处理与安全性

- 初始化开始前不修改统计视图或存档结构。
- 协调器初始化抛出异常时恢复所有已修改引用和容量覆盖。
- 生命周期补丁不得向 `TileMgr.Update` 传播异常，避免因 Mod 导致游戏帧循环中断。
- 日志分别记录插件加载、会话初始化成功、首次初始化失败和后续重试。
- 安装 v0.1.1 前备份当前插件 DLL。
- 不自动改写或回滚任何用户存档。

## 测试设计

### 自动测试

通过一个不依赖 Unity 帧循环的会话初始化门控组件覆盖：

- 游戏仍在载入时不初始化。
- 载入结束后初始化一次。
- 同一管理器的后续轮询不会重复初始化。
- 管理器切换后重置并初始化新会话。
- 初始化失败后保持未就绪，并在下一次轮询重试。
- 管理器消失时重置会话。

保留并运行现有库存合并、主仓选择、嵌套单仓视图、异常恢复和容量测试。

### 静态集成检查

- v0.1.1 程序集包含 `TileMgr.Update` Harmony 补丁。
- `Plugin` 不再声明 Unity `Update()` 轮询入口。
- 插件 GUID 保持 `cn.ratopia.sharedwarehouse`，版本更新为 `0.1.1`。

### 游戏内验收

1. BepInEx 只加载“共享仓库”v0.1.1，日志无 Harmony 安装错误。
2. 完成读档后日志出现一次“共享仓库初始化完成”。
3. 仓库与迷你仓库显示“当前种类数/∞”。
4. 在一座仓库存入材料，另一座立即可见并能取出。
5. 新建仓库立即接入共享库存。
6. 建造判断、材料统计、食物统计和账本不按仓库数量重复。
7. 保存、退出、重新读档后材料总数不因仓库数量再次倍增。

## 交付

- Release 构建程序集 `SharedWarehouse.dll`，版本 0.1.1。
- 安装到 `E:\steam\steamapps\common\Ratopia\BepInEx\plugins\SharedWarehouse`。
- 更新 Nexus Mods 安装包和说明文档。
- 不打包任何游戏、Unity、BepInEx 或 Harmony DLL。
